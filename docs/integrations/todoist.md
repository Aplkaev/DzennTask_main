# Todoist — эскиз (держим в уме)

Статус: не в активной разработке. Общая модель — см. `README.md`. Хороший кандидат на "второй провайдер"
после Битрикс24 — проверить, что абстракция адаптера реально не завязана на специфику одного сервиса.

## Auth

- Для личного использования — Personal Access Token (создаётся в настройках аккаунта Todoist, без
  OAuth-плясок), аналогично входящему вебхуку Битрикса по простоте.
- Если когда-нибудь понадобится подключать чужие аккаунты (не только свой) — Todoist поддерживает
  полноценный OAuth 2.0, App Management Console.

## Push-механизм

Todoist Webhooks (настраиваются там же, в App Management Console) — реалтайм пуши по событиям
`item:added`, `item:updated`, `item:completed`, `note:added` (комментарии). Ближе по устройству к
Битрикс24 (`event.bind`), чем к Telegram.

## Маппинг полей

| DzennTask (Task) | Todoist            | Примечание |
|--------------------|---------------------|------------|
| `title`             | `content`           | |
| `description`       | `description`       | |
| `deadline`           | `due.date`          | |
| `status`             | `checked` (bool)    | Todoist — плоская модель "выполнено/нет", без промежуточных статусов Битрикса → маппинг сильно упрощённый, обратный маппинг (`Task.status` → Todoist) неоднозначен для промежуточных статусов |
| комментарии          | `notes` (item notes)| |

`priority` Todoist (1–4) **не мапим** на локальный `priority` — по общему правилу (см. `README.md`)
приоритет/спринт остаются только локальными полями, но здесь стоит явно решить: игнорировать входящий
`priority` Todoist полностью, или использовать его только как значение по умолчанию при первом импорте
(дальше — не синкать). Оставлено как решение на момент реализации.

## Зачем этот провайдер, если есть Битрикс24

Todoist — пример сервиса без командной специфики (Битрикс — командный портал), полезен как проверка,
что модульность работает и для персональных to-do сервисов, не только для корпоративных трекеров.
