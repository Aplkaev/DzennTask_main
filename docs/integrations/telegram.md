# Telegram — эскиз (держим в уме)

Статус: не в активной разработке, идея зафиксирована на будущее. Общая модель — см. `README.md`.

## Кейс

Не CRUD-синк с трекером, а **ingestion**: неформальные задачи, которые в реальности живут в переписке
(личка, рабочий чат), а не в трекере. Отличается от Битрикс24/Todoist по сути — там мы синкаем
существующие задачи, здесь мы **создаём** задачу из сообщения.

## Auth и транспорт

- Telegram Bot API, `bot_token` — без OAuth, максимально просто для личного использования.
- Push — `setWebhook` на наш публичный HTTPS-эндпоинт, апдейты (`message`, `edited_message`,
  `message_reaction`) прилетают сразу, поллинг не нужен.

## Направление синка

В основном одностороннее: Telegram → `Task`. Обратная связь опциональна — бот может ответить в чат при
смене статуса задачи ("✅ задача выполнена").

## Что синкать

- Текст сообщения → `title`/`description` (нужно решить разбиение: например первая строка — title,
  остальное — description).
- Отправитель → `externalAuthorName` (тот же паттерн, что для внешних авторов комментариев Битрикса —
  см. `README.md`), если отправитель — не пользователь DzennTask.
- Пересланные файлы → `Attachment`, но **с оговоркой**: `file_id` Telegram недолговечен и не является
  публичной постоянной ссылкой (в отличие от Битрикс-Диска) — файл нужно скачать и перезалить куда-то
  у себя (или в S3-совместимое хранилище) сразу при получении, иначе ссылка отвалится.

## Открытый вопрос: как определять "это команда создать задачу"

Варианты, не выбран ни один:
- Явная команда `/task <текст>`.
- Реакция определённым эмодзи на сообщение.
- Пересылка сообщения боту в личку (переслал — значит "в задачи").

Разные варианты дают разный UX и разную сложность реализации, выбор — когда дойдут руки до этого
провайдера.
