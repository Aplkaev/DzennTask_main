# Битрикс24 — план реализации

Статус: первый провайдер в очереди, реальный рабочий кейс (Битрикс24 на работе). Ниже — конкретный,
готовый к реализации план, не общие рассуждения.

## Способ подключения: входящий + исходящий вебхук (не локальное приложение)

Изначально планировалось локальное приложение (OAuth), но на практике на портале автора (тариф
"Профессиональный") раздел создания локальных приложений недоступен. Причина не до конца ясна —
похоже на отдельную подписку "Маркет", не входящую автоматически даже в платные CRM-тарифы, но это
не подтверждено официальной документацией однозначно; при желании прояснить точно — раздел портала
"Мой тариф" → "Маркет" или обращение в `helpdesk.bitrix24.ru`. Разбираться в этом не обязательно —
есть рабочая альтернатива, доступная на текущем тарифе.

Есть два варианта аутентификации к Битрикс24:

1. **Входящий + исходящий вебхук** — создаются в пару кликов в админке портала, никакого OAuth и
   раздела "Мои приложения". Входящий вебхук закрывает все исходящие вызовы (аналог access-токена без
   протухания), исходящий вебхук — ручной аналог `event.bind`: подписка на событие настраивается в UI,
   а не программным вызовом, но по факту даёт тот же реалтайм-пуш. Доступны на платных тарифах (в т.ч.
   Professional), в отличие от бесплатного.
2. **Локальное приложение** (Bitrix24 → Разработчикам → Другое → Локальное приложение) — полноценный
   OAuth (access + refresh токен). Недоступно на текущем тарифе портала — оставлено как возможный путь
   на будущее (если появится нужная подписка, или понадобится подключать чужие порталы, не только свой
   рабочий).

**Берём вариант 1** — он закрывает ту же задачу (реалтайм синк) и работает прямо сейчас, без OAuth-обвязки
(нет install-flow, нет refresh-токена).

## Пререквизиты

- Публичный HTTPS-адрес для хендлера, принимающего исходящие вебхуки. Битрикс не умеет стучаться на
  `localhost`. Для разработки — туннель (Cloudflare Tunnel / ngrok), в проде — обычный домен.
- Права (scope) входящего вебхука: `task`, `im` (уведомления, опционально), `disk` (файлы задач), `user`
  (резолвить автора комментария/исполнителя).

## Шаги настройки в самом Битрикс24 (вручную, один раз на портал)

1. Портал → Разработчикам → Другое → **Входящий вебхук** → выбрать права из списка выше → получить URL
   вида `https://domain.bitrix24.ru/rest/{user_id}/{webhook_code}/`.
2. Портал → Разработчикам → Другое → **Исходящий вебхук** → создать **по одной штуке на каждое событие**:
   `ONTASKADD`, `ONTASKUPDATE`, `ONTASKDELETE`, `ONTASKCOMMENTADD` — указать наш Handler URL. В отличие
   от `event.bind` у локального приложения (одна регистрация — все события программно), тут это ручная
   настройка на портале, но делается один раз.
3. Оба URL/токена вставляются пользователем DzennTask на шаге `connect` (см. ниже) — регистрировать
   ничего программно через Bitrix API не нужно.

## Подключение — что должен делать `/integrations/bitrix24/connect`

Пользователь уже авторизован в DzennTask, вставляет входящий webhook URL и выбирает `project_id`,
к которому привязать интеграцию:

1. Проверка **до** записи в БД: `SELECT ... WHERE project_id = :id` — если у проекта уже есть
   интеграция, вернуть понятную ошибку ("к проекту уже подключена другая интеграция"), а не полагаться
   только на 500 от unique constraint (constraint — это подстраховка, не основной путь).
2. Провалидировать сам webhook URL реальным вызовом (например `profile` или `app.info`) — прежде чем
   сохранять, убедиться что он рабочий и права выданы верно.
3. Создать `ProjectIntegration`: `provider = bitrix24`, `credentials` (webhook URL — это и есть
   единственный секрет, отдельного access/refresh токена нет), `status = active`.
4. Сделать первый полный поллинг (`tasks.task.list`) для начального наполнения проекта задачами.

## Хранение секрета

- Единственный секрет — URL входящего вебхука (содержит `user_id` + `webhook_code`). Хранить
  **шифрованным** в БД, как любой долгоживущий доступ к рабочему порталу — по сути это bearer-токен,
  зашитый прямо в URL.
- Ротация — пользователь может в любой момент перевыпустить вебхук в UI Битрикса (старый перестанет
  работать) — предусмотреть на своей стороне понятную ошибку авторизации (`status = error` у
  `ProjectIntegration`) и предложение вставить новый URL, а не тихий сбой синка.
- Никакого фонового job на refresh токена не нужно — этим и проще OAuth-варианта.

## Какие события подписываем (исходящие вебхуки)

- `ONTASKADD`, `ONTASKUPDATE`, `ONTASKDELETE`
- `ONTASKCOMMENTADD` (и по возможности `ONTASKCOMMENTUPDATE`/`ONTASKCOMMENTDELETE`, если Битрикс их шлёт
  для задач — надо сверить в актуальной документации на момент реализации, историческая нестабильность
  этого API у Битрикса известна)

Важно: событие от Битрикса — это **не** полный объект задачи, а только `{event, data: {FIELDS_BEFORE,
FIELDS_AFTER}}` либо просто id. Поэтому обработчик вебхука не апсертит задачу из пейлоада напрямую, а:

1. Валидирует `auth[application_token]` из тела запроса (сверка с токеном, который Битрикс выдаёт при
   создании исходящего вебхука и который сохраняется у нас на шаге `connect` — точный формат сверить в
   документации на момент реализации, это подтверждает, что вызов реально от Битрикса, а не подделан).
2. Кладёт событие в очередь (Messenger) — сам HTTP-хендлер должен отвечать быстро, тяжёлую работу не
   делает.
3. Consumer по событию вызывает `tasks.task.get` за полным состоянием задачи и уже потом
   апсертит `Task` + `TaskExternalLink`.

## Исходящий синк (наши изменения → Битрикс)

Переиспользуем существующий паттерн `EntitySubscriber`/outbox: локальное изменение `Task.status` (или
добавление `Comment`), если у задачи есть `TaskExternalLink` на Bitrix-интеграцию — создаёт событие,
отдельный consumer вызывает:

- `tasks.task.update` (поле `STATUS`) — при смене статуса.
- `task.commentitem.add` — при новом комментарии.

Локальные-only поля (`priority`, `storyPoints`, `kanbanColumn`) никогда не уходят в Битрикс — см.
`README.md`.

## Маппинг полей

| DzennTask (Task)     | Битрикс24 (tasks.task)        | Примечание |
|-----------------------|--------------------------------|------------|
| `title`               | `TITLE`                        | |
| `description`         | `DESCRIPTION`                  | Битрикс отдаёт BB-код/HTML, нужна нормализация в текст/markdown |
| `status`               | `STATUS`                       | Числовой enum Битрикса (2=Ждёт, 3=В работе, 4=На проверке, 5=Завершена...) → маппинг на `TaskStatusEnum`, не 1:1 |
| `deadline`             | `DEADLINE`                     | |
| комментарии            | `task.commentitem.*`           | Автор — резолвится через `user.get` по `AUTHOR_ID`, если это не наш `User` → `externalAuthorName` |
| файлы                  | `UF_TASK_WEBDAV_FILES` (Диск)  | Храним только ссылку, не перекачиваем (см. `README.md`) |

## Лимиты и надёжность

- Rate limit Битрикс24 REST — ориентировочно 2 запроса/сек на портал. Исходящие вызовы должны идти через
  очередь с ограничением конкурентности (Messenger + rate limiter), не параллельным веером.
- Вебхуки ненадёжны сами по себе (сетевые сбои, рестарт нашего сервиса в момент доставки) — обязателен
  fallback-поллинг: раз в N минут `tasks.task.list` с фильтром `>UPDATED_DATE` по всем активным
  `ProjectIntegration` для реконсиляции с тем, что могло потеряться.

## Поэтапный план

1. **MVP** — только вход. `connect`-эндпоинт (вставить входящий webhook URL + выбрать проект), ручная
   кнопка "синхронизировать" (без исходящих вебхуков), одностороннее подтягивание задач
   (title/description/status/deadline), без комментариев и файлов.
2. **v1** — исходящие вебхуки, реалтайм вход, обратный push статуса и комментариев.
3. **v2** — файлы (ссылки на Диск), маппинг исполнителя (`assigned_to`) на `User`/внешнего человека,
   fallback-поллинг для реконсиляции.

## Открытые вопросы (решить перед стартом реализации)

- Нужен публичный HTTPS-домен уже на этапе разработки — без него исходящие вебхуки не протестировать
  локально. Определиться с туннелем/доменом до старта кодинга.
- Точный формат подтверждения подлинности исходящего вебхука (поля `auth[...]` в payload) — сверить
  в актуальной документации на момент реализации, не полагаться на память из этого плана.
- Что если пользователь хочет привязать **несколько** Bitrix-порталов (например, если сменит работу)?
  Текущая модель это не запрещает — просто разные `Project` с разными `ProjectIntegration`, но нет UI
  для "показать все мои Bitrix-подключения" — вопрос UX, не архитектуры.
- Что делать, если задачу пытаются привязать к проекту, где уже есть задача с тем же `externalId`
  (повторное создание вебхука, дублирующийся вызов) — нужна идемпотентность upsert по
  `(project_integration_id, externalId)`.
- Если позже откроется доступ к локальным приложениям (появится нужная подписка) — можно будет перейти
  на OAuth-вариант ради программной регистрации событий вместо ручной настройки 4 исходящих вебхуков,
  но это не блокирует текущий план.
